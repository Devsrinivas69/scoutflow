# ScoutFlow — Render.com Hosting Guide

This guide provides step-by-step instructions on deploying ScoutFlow to [Render.com](https://render.com) using the blueprint specification (`render.yaml`).

---

## Architecture Overview

ScoutFlow is configured to deploy with three resources on Render:
1. **`scoutflow-redis` (Key-Value Database)**: Powers the BullMQ background job queues and the lookalike caching layer.
2. **`scoutflow-web` (Web Service)**: Hosts the Next.js user interface and the API endpoints.
3. **`scoutflow-worker` (Background Worker)**: Handles the heavy lifting of the search, enrichment, and email delivery pipelines.

All configurations are consolidated into a single shared environment variable group (`scoutflow-shared`).

---

## Step-by-Step Deployment Guide

### Step 1: Push the Configuration changes to GitHub
Render deploys directly from your GitHub repository. Commit and push the new blueprint file:
```bash
git add render.yaml render_deployment_guide.md
git commit -m "chore: add render.yaml blueprint and deployment guide"
git push origin master
```
*Note: Make sure `.env` remains in your `.gitignore` so secrets are never pushed to GitHub.*

### Step 2: Deploy Blueprint on Render
1. Log in to the [Render Dashboard](https://dashboard.render.com).
2. Click **New +** in the top right corner and select **Blueprint**.
3. Connect your GitHub repository containing the ScoutFlow project.
4. Give your Blueprint group a name (e.g. `scoutflow-production`).
5. Render will automatically parse the `render.yaml` file and list the resources it will provision.

### Step 3: Populate Environment Variables
Render will prompt you to fill in the environment variables defined in the `scoutflow-shared` group. Populate them using the values from your local `.env` file:

| Environment Variable | Description / Value | Action |
| :--- | :--- | :--- |
| **`DATABASE_URL`** | Your Supabase Connection Pooler URL (IPv4). | **Required** (Use the Session-mode connection pooler string, e.g., `postgresql://postgres.xlbdumkvoplnnkiqkrnz:PASSWORD@aws-0-[REGION].pooler.supabase.com:5432/postgres`. Do not use the direct connection string, as Render is IPv4-only and direct Supabase hostnames default to IPv6.) |
| **`NEXTAUTH_SECRET`** | Auto-generated by Render. | Leave blank (Render auto-populates this with a secure value) |
| **`AUTH_SECRET`** | NextAuth v5 secret (auto-generated by Render). | Leave blank (Render auto-populates this with a secure value) |
| **`NEXTAUTH_URL`** | The URL of your web service. | Enter your assigned Render URL (e.g. `https://scoutflow-web.onrender.com`) |
| **`AUTH_URL`** | NextAuth v5 canonical URL. | Enter your assigned Render URL (e.g. `https://scoutflow-web.onrender.com`) |
| **`AUTH_TRUST_HOST`** | Proxy trust indicator. | Set to `true` in environment group to allow reverse proxy operations on Render |
| **`NEXT_PUBLIC_SUPABASE_URL`** | Your Supabase API URL. | **Required** (e.g. `https://xlbdumkvoplnnkiqkrnz.supabase.co`) |
| **`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`** | Supabase publishable key. | **Required** |
| **`OCEAN_API_KEY`** | Ocean.io API Key. | **Required** |
| **`PROSPEO_API_KEY`** | Prospeo API Key. | **Required** |
| **`RESEND_API_KEY`** | Resend API Key. | **Required** |
| **`RESEND_FROM_NAME`** | Name displayed in outreach emails. | Already set to `ScoutFlow` in blueprint. (Can override) |
| **`RESEND_FROM_EMAIL`** | Verified Resend email address. | **Required** (e.g. `contact@scout-flow.app`) |
| **`RESEND_REPLY_TO`** | Reply-To email address. | Optional (e.g. `contact@scout-flow.app`) |
| **`APOLLO_API_KEY`** | Apollo API Key. | Optional fallback key |

Click **Apply** to start provisioning.

### Step 4: Verify Deployment Status
1. **Database Schema Sync**: During deployment, the `scoutflow-web` service will run `prisma db push` to synchronize your Supabase database schema automatically.
2. **Health Check**: Once deployed, visit `https://YOUR-APP-NAME.onrender.com/api/health`. It should return a `200 OK` JSON response:
   ```json
   {
     "status": "healthy",
     "timestamp": "2026-06-08T21:10:00.000Z",
     "services": {
       "database": { "status": "healthy" },
       "redis": { "status": "healthy" }
     }
   }
   ```
3. **Queue Processing**: Trigger a lookalike run in the ScoutFlow UI. Go to the **scoutflow-worker** service logs in the Render dashboard and verify that the worker picks up the job and processes it successfully.

## Production Recommendations

* **Redis Persistence**: The `free` Redis plan does not persist data to disk and spins down after periods of inactivity. For production pipelines where queue state is critical, upgrade the `scoutflow-redis` service to the `starter` tier.
* **NextAuth URL**: If you setup a custom domain in Render, remember to update the `NEXTAUTH_URL` variable in your shared environment group to point to the new domain.
